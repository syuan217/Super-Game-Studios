# ZCode Support

This template runs on both **Claude Code** and **ZCode**. `.claude/` is the
single source of truth for both; the ZCode layer (`.zcode/`, root `AGENTS.md`,
`tools/zcode/`) is generated or hand-maintained as described below. Nothing in
`.claude/` is modified by the ZCode adaptation, so upstream merges stay
conflict-free.

## Architecture

```
.claude/                    # Source of truth (Claude Code native, unchanged)
  agents/  skills/  hooks/  rules/  settings.json
.zcode/                     # Generated layer (committed, do not hand-edit)
  agents/                   #   49 agents, generated by tools/zcode/sync.sh
  skills/                   #   73 skills, generated by tools/zcode/sync.sh
  config.json               #   Hook wiring (hand-maintained)
AGENTS.md                   # ZCode workspace instructions (hand-maintained)
tools/zcode/
  sync.sh                   #   Regenerates .zcode/agents + .zcode/skills
  hook-adapter.sh           #   Wraps SessionStart stdout into additionalContext JSON
  guard-deny.sh             #   Replicates the Claude deny permission list
```

After merging upstream changes: run `bash tools/zcode/sync.sh`, then commit the
regenerated `.zcode/` tree.

## Mechanism mapping

| Claude Code mechanism | ZCode counterpart | Status |
|---|---|---|
| `CLAUDE.md` (+ `@import`) | Root `AGENTS.md` with explicit read-before-X pointers | Migrated |
| `.claude/agents/` auto-registration | `.zcode/agents/` scanned recursively, registered natively, default-enabled | Migrated (49) |
| `.claude/skills/` | `.zcode/skills/` | Migrated (73, one rename) |
| Agent frontmatter `tools` / `disallowedTools` / `maxTurns` / `skills` | Same keys parsed and runtime-enforced | Migrated |
| `.claude/settings.json` hooks | `.zcode/config.json` → `hooks.events` (`hooks.enabled: true`) | Partial (see below) |
| Path-scoped rules (`.claude/rules/`) | No ZCode equivalent — mapping table in `AGENTS.md`, read on demand | Downgraded to convention |
| Folder memory (`design/CLAUDE.md` etc.) | Only root `AGENTS.md` auto-loads — table in `AGENTS.md` | Downgraded to convention |
| `permissions.allow/deny` | No workspace permission rules — deny list replicated by `guard-deny.sh` (allow list not replicated) | Partial |
| `statusLine` | No ZCode equivalent | Dropped |
| Skill frontmatter `allowed-tools` / `argument-hint` / `user-invocable` / `model` / `agent` / `context` / `isolation` | ZCode parses `name/description/when_to_use/license/metadata` only | Stripped (see below) |

## Known behavioral differences

- **Skill name collision** — CCGS `/code-review` is generated as
  `ccgs-code-review` because a personal user-scope skill named `code-review`
  would otherwise shadow it (user scope wins over workspace scope in ZCode).
  Cross-references inside skill bodies still say `/code-review`.
- **`agent:` skill frontmatter (20 skills)** — on Claude Code these skills run
  inside that subagent; on ZCode they run in the main conversation. Bodies are
  unchanged; deep agent-bound work can be dispatched manually.
- **`context:` frontmatter (3 skills: changelog, help, sprint-plan)** — Claude
  executes the embedded `!shell` commands at skill load and injects the output;
  ZCode has no equivalent, so those skills gather the same state via their own
  tool calls.
- **`isolation: worktree` (prototype, vertical-slice, prototyper agent)** —
  ZCode runs them in the main workspace; no git-worktree isolation.
- **Model tiering** — `model: opus/sonnet/haiku` hints cannot map to ZCode
  models and are stripped; every agent and skill runs on the session model.
- **`memory: user` (17 agents)** — no cross-session per-agent memory on ZCode.
- **SessionStart stdout** — ZCode expects strict-JSON
  `{"additionalContext": ...}`; `hook-adapter.sh` provides the envelope. If a
  future ZCode build injects plain stdout directly, the adapter can be removed.
- **Auto-compaction** — whether ZCode's automatic context management emits a
  `compact`-source SessionStart (and thus fires post-compact.sh) is unverified;
  if not, the hook silently never fires (harmless).
- **Hook matcher must be non-empty** — ZCode's config schema requires
  `matcher` strings to have at least 1 character; `"matcher": ""` fails the
  whole config file (every hook silently unregisters). To match everything,
  **omit** the `matcher` field entirely.
- **Workspace hooks pass a trust gate on first load** — after ZCode loads
  `.zcode/config.json` it marks the hooks `pending_trust`
  (`config.project_hooks.pending_trust` in the log) and prompts for approval
  per hook command before they run. Editing `config.json` changes the bundle
  digest and re-triggers the prompt. This is expected, not a failure.
- **Settings → Subagents UI shows user-scope agents only** — workspace agents
  from `.zcode/agents/` are registered in the session's Agent tool but do not
  appear in that settings view. Verify registration by using the agent, not by
  browsing the UI. (Verified empirically: a session's model request contained
  the full 49-agent list in the Agent tool description even though the UI does
  not list them.)

## Verification checklist (after a fresh ZCode session in this repo)

1. `/` menu shows the CCGS skills (including `ccgs-code-review`, not
   `code-review`).
2. Ask the model to spawn a studio agent, e.g. "use the Agent tool with
   subagent_type qa-tester to summarize what it would do" — the call must
   succeed. (Do not rely on the Subagents settings UI; it lists user-scope
   agents only.)
3. Session start shows the studio context block (branch, recent commits,
   stage).
4. `rm -rf /tmp/test-guard` as a Bash call is blocked with a `guard-deny` reason.
5. A `git commit` attempt triggers commit validation warnings when staging
   invalid design docs or JSON.
6. `~/.zcode/cli/log/zcode-<date>.jsonl` contains no `config.file.invalid`
   entries after startup, and PreToolUse hook executions appear.
7. Claude Code sessions in the same repo are unaffected (`git status` shows no
   `.claude/` changes).
